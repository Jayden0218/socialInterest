# Load Measurement — 2026-09-06 — 003/US5 (T045, T046, T047)

Taken against the **durable** stack (disk-backed volumes), after 003/US2. Not edited after
the run.

## What this is a measurement of

**DynamoDB Local.** Not the product, not the read-time feed design, not what either would do
in service. That sentence is the point of this record, not a caveat at the end of it
(003/FR-013).

Feature 001 reported an emulator's p95 of 11.8s as a property of the read-time feed design,
and that reading drove a proposal to build a fan-out hybrid the evidence never supported.
`002/SC-002` (10,000 concurrent) remains **unverified** and only a provisioned datastore can
close it — which needs the owner's explicit approval to spend.

## Ceiling attribution — `bench:ceiling` (T045)

The three limits measured apart, so the lowest one is identified rather than assumed.

| Subject | peak req/s |
|---|---|
| generator (the load client alone) | 356,276 |
| **datastore** (DynamoDB Local, real round trip) | **882** |
| application shape (the API with the datastore replaced by a fixed delay) | 9,475 |

**Lowest ceiling: the datastore, at 882 req/s** — an order of magnitude below the application
shape and four below the generator.

For comparison, the 2026-09-05 run against the `-inMemory` stack gave 187,439 / 827 / 5,574.
Putting the datastore on disk did not make it the bottleneck; it already was, and remains so
by the same margin. Neither set of figures says anything about D1.

## Feed under concurrency — `bench:feed-load` (T046)

`transport: http`, `datastore: DynamoDB Local (http://127.0.0.1:8000)`, version `c38af0a`,
budget p95 ≤ 2000ms, 40 requests per level, **0 errors at every level**.

| concurrency | n | p50 | p95 | p99 | req/s | errors |
|---|---|---|---|---|---|---|
| 1 | 40 | 51.9 | 77.0 | 92.1 | 19 | 0 |
| 10 | 40 | 346.2 | 484.8 | 513.8 | 27 | 0 |
| 50 | 40 | 1009.0 | 1376.0 | 1382.4 | 29 | 0 |
| 100 | 40 | 1262.1 | 1407.8 | 1413.9 | 28 | 0 |

- **first breach of the 2000ms p95 budget**: none at the levels tested
- **binding constraint**: the datastore
- **evidence**: throughput flattens at ~29 req/s from concurrency 10 onward while p95 rises
  from 77ms to 1408ms. Throughput that stops growing while latency grows linearly is a
  saturated dependency, not an algorithm out of headroom — and `bench:ceiling` above says
  which dependency.

## Three defects in the bench itself, found by running it

None of these were visible from reading it, and two produced a *report* rather than a failure.

1. **The API's stderr was piped and never drained.** A pipe holds ~64KB; once Nest had written
   that much the API blocked on its next write and stopped answering. The bench sat on a fetch
   that would never return — 22 minutes with no output, because the report prints at the end.
   Output goes to a file now. `apps/e2e/support/api-process.ts` already carried this exact
   lesson in a comment; this file did not.

2. **`stop()` killed the `npx` wrapper, not the server.** `npx` spawns `tsx` spawns `node`, so
   the actual server survived every run and kept the port.

3. **The next run adopted that orphan.** The health probe accepted it, the bench never started
   its own API, and because the orphan's `LOCAL_JWT_SECRET` differed, **every request 401'd** —
   and the run printed a table of `p50 0, p95 0, p99 0` with `bottleneck: datastore` beneath
   it. 160 errors, 0 successes, reported as a measurement. Zeros read as "fast".

Fixed in three places: the bench refuses to adopt a process it did not start, kills the whole
process group, and `reportMeasurement` now throws rather than print a run in which nothing
succeeded — or one where failures outnumber successes.

The attribution string also recited "~827 req/s versus ~5,574" from a previous session as
though it had just been measured. Those numbers went stale (882 and 9,475 today) while the
sentence kept stating them with the authority of a measurement. It now names only what this
run observed and points at `bench:ceiling` for the rest.
