## The measurement that was the whole diagnosis

```
013/T001: 8 simultaneous creations of one name -> 8 accepted, 8 in the table
                       ... after the claim row -> 1 accepted, 1 in the table
```

Not a race. **No constraint at all** — `createSubInterest` guarded
`attribute_not_exists(pk)` on a fresh ULID, which can never fire for a name, and
what stood in for it was a read against a **per-process** cache. 011's handle
defect word for word. A fix aimed at narrowing a window would have been progress
against the wrong diagnosis; the before-and-after pair is the evidence.

## Six defects no plan predicted

1. **`loadAll()` walked the hierarchy** through the index this feature deletes,
   so the cache loaded **empty** and the duplicate gate accepted everything.
   The feature's own failure mode, arriving through the loader rather than the
   comparison. **The unit guard could not see it** — it stubs `loadAll`, which is
   007's `ApiPage` defect in miniature: a stub agreeing with the test and not
   with the datastore. An integration test caught it.
2. **The 409 stopped carrying its candidates.** The removed interest controller
   attached them; the publish route did not. FR-009/FR-010 exist so a client can
   offer "join this one instead" — a bare refusal is the sprawl control doing
   nothing. Caught within the minute.
3. **`expandInterests` validated ids against the catalogue**, and an interest
   created inside the transaction is not there yet — every genuinely new name
   returned 422.
4. **The harness picked a retired interest** once the listing stopped filtering
   by level, so ~40 unrelated suites failed at their first publish.
5. **`postCount` is never maintained.** `incrementPostCount` has no caller
   anywhere, so it is 1 for every interest for ever. Retiring on `postCount === 0`
   would have retired nothing and looked implemented. Housekeeping reads the
   index **rows**.
6. **The migration refused to run**, correctly: it found 3 name collisions, all
   of them duplicates T001's own measurement had just created.

## Two decisions taken against the plan, on evidence

- **The merged name's claim is NOT released.** The plan said to release it so
  the name was not permanently burnt. Writing the test showed that is worse:
  `resolveOrPrepare` row 4 already lands a person on the survivor, and releasing
  the claim would let the next person **recreate the duplicate the merge
  removed**. A releaser with no caller would have been the declared-half shape.
- **`POST /v1/interests` is removed**, which moves the route snapshot. It wrote
  `postCount: 0`, the state FR-004 makes unrepresentable. Research R5 named this
  consequence before the work started; FR-025 calls for a deliberate, reviewed
  edit, and this is it.

## Still open

- **T037**: whether an interest "has posts" when its last post is hidden by its
  author or removed by a moderator rather than deleted. That is a **visibility**
  question and the boundary must answer it — a job counting rows the boundary
  would withhold would be a second visibility decision, which Principle II
  forbids. `retireIfEmpty` reads rows RAW today, which is right for "does any
  post exist" and is **not** an answer to the hidden case.
- **The mobile compose screen names an interest but does not yet offer the
  candidates** a 409 returns. The server carries them (FR-009); the client does
  not show them. That is the other half of T021.
- **No device run**, and **MinIO-dependent paths** (`ports.contract`,
  `us1-exif`, the quickstart, the real CI list) cannot run here. Both API
  failures were baselined by stashing the change and watching them fail
  identically.
