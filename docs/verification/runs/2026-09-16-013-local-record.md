## The measurement that was the whole diagnosis

```
013/T001: 8 simultaneous creations of one name -> 8 accepted, 8 in the table
                       ... after the claim row -> 1 accepted, 1 in the table
```

Not a race. **No constraint at all** — `createSubInterest` guarded
`attribute_not_exists(pk)` on a fresh ULID, which can never fire for a name, and
what stood in for it was a read against a **per-process** cache. 011's handle
defect word for word. A fix aimed at narrowing a window would have been progress
against the wrong diagnosis; the before-and-after pair is the evidence.

## Six defects no plan predicted

1. **`loadAll()` walked the hierarchy** through the index this feature deletes,
   so the cache loaded **empty** and the duplicate gate accepted everything.
   The feature's own failure mode, arriving through the loader rather than the
   comparison. **The unit guard could not see it** — it stubs `loadAll`, which is
   007's `ApiPage` defect in miniature: a stub agreeing with the test and not
   with the datastore. An integration test caught it.
2. **The 409 stopped carrying its candidates.** The removed interest controller
   attached them; the publish route did not. FR-009/FR-010 exist so a client can
   offer "join this one instead" — a bare refusal is the sprawl control doing
   nothing. Caught within the minute.
3. **`expandInterests` validated ids against the catalogue**, and an interest
   created inside the transaction is not there yet — every genuinely new name
   returned 422.
4. **The harness picked a retired interest** once the listing stopped filtering
   by level, so ~40 unrelated suites failed at their first publish.
5. **`postCount` is never maintained.** `incrementPostCount` has no caller
   anywhere, so it is 1 for every interest for ever. Retiring on `postCount === 0`
   would have retired nothing and looked implemented. Housekeeping reads the
   index **rows**.
6. **The migration refused to run**, correctly: it found 3 name collisions, all
   of them duplicates T001's own measurement had just created.

### The contract had stopped describing the product, in five places

`POST /interests` was removed from the server and the document still declared
it. Removing it took the generated client from **93 operations to 92** — and the
92 is what found the rest:

1. **`PostCreate` did not declare `interestNames` or `acknowledgedSimilarTo`,
   and REQUIRED `interestIds`.** 013's entire premise was absent from the
   contract: a client generated from it could not name an interest at all, and
   was obliged to send ids for a gesture that has none. It works from the app
   only because `apps/mobile/src/data/posts.ts` declares the field by hand.
2. **`POST /posts` did not declare the 409.** The near-duplicate refusal moved
   to the publish route with the gesture; the document still said 201/422/429,
   so the sprawl control was invisible to any generated client. Found by MOVING
   the contract assertion rather than deleting it.
3. **`GET /interests/similar` declared `parentId` as REQUIRED** while the server
   had stopped reading it — the controller's own comment says demanding one
   "would have made this endpoint unreachable from a compose screen that has
   none", and the contract was demanding it the whole time.
4. **`GET /interests` declared `level` and `parentId`**, both accepted and
   ignored end to end — controller, `InterestSearch`, `InMemoryCatalogueCache`.
   An accepted-and-ignored filter is one a caller cannot tell from a filter that
   matched everything. Removed from the signature, not left unread.
5. **`InterestCreate` and `InterestDetail.subInterests`** described a create
   route and a hierarchy that no longer exist.

### And three dead halves in the code

- **`InterestContainer` still CALLED `data.interests.listChildren(interestId)`**
  on every interest screen open and threw the result away, under a comment
  saying interests are flat. A request per open, carrying a `parentId` the
  server ignores, for a list nothing renders. Deleting the METHOD is what turns
  the dead call into a typecheck failure rather than a comment.
- **`createInterestSchema` survived its route's removal** as an unreferenced
  const — still making `parentId` mandatory, the single field 013 exists to
  remove.
- **Two doc comments still described the curated tier** ("operators for a
  top-level interest; the creator for a sub-interest"), on the server and in the
  mobile data layer, after the code stopped making that distinction. 007's rule:
  when a requirement is withdrawn, grep the COPY, not only the code.

### The e2e journeys, rewritten rather than deleted

`interests.create` is gone, so nine call sites had to create an interest the way
a person now does. `publishReadyNamingInterest` in `apps/e2e/support/publish.ts`
is that gesture, and the fixture post it publishes IS the create — so the
ordering tests that counted four posts still count four.

Two tests drove withdrawn behaviour and were **replaced, not removed**, because
deleting them would have taken a live guarantee with them:

- "a top-level interest is curated: only an operator may describe it" → **an
  operator may describe an interest they did not create.** The stranger's
  refusal is asserted separately; the operator half had no other cover.
- the browser gate's "the space lists a sub-interest post and says where it came
  from" (001/FR-024's roll-up) → **an interest a person NAMED is findable by
  search and its space holds the post that created it.** Same navigational
  guarantee, for the product that exists now — and 013 is exactly the change
  that makes every interest a person-named one.

One fixture is worth naming: `post-search`'s FR-022 fallback publishes with **no
caption**, and the missing caption is the point. Post search indexes caption
terms only, so a captionless post leaves the nonce unfindable as a post while
the interest carrying it is findable — which is the miss the test needs.

## Two live product defects, both found by a request

1. **`POST /v1/posts` returned the PERSISTENCE ROW.** `authorId`, `interestIds`
   and `updatedAt` went out; `author`, `interests` and `media` did not. The
   contract declares all three and requires two, so a generated client reads
   `undefined` and `post.interests.map` throws. Seventh instance of this shape
   here — and the comment forty lines below it, "Not `{ ...result.post }`: that
   is the persistence row", was written about the DETAIL route while this one did
   exactly that. The app reads only `postId` from a publish, which is why five
   features went by.
2. **An update that moved a row between indexes did not move it.** `runUpdate`
   issued `update items set item = <jsonb>` and never touched the key COLUMNS,
   which every query reads. On DynamoDB there was no distinction. It cost two
   journeys, both silent: accepting a conversation left it out of the accepted
   inbox, and leaving a group left it in. Neither was a product bug — both
   writes were right. Guarded by a QUERY, not a read, because a read passes
   throughout.

## 012 Phase 6 and Phase 8

- **`Photo`** gives a photograph the four-state rule (FR-006a). `naturalWidth`
  could not be used to verify it and the first version used it anyway:
  react-native-web renders an `Image` as a div with a CSS background. Measured,
  then replaced with the two things this renderer can answer — the app's own
  placeholder detaching, and a fetch of the presigned url (200, image/jpeg,
  non-zero bytes).
- **`postCount` finally has a writer**, in the publish transaction beside the
  index rows it counts and the delete transaction beside their removal.
  Interests are created at 0 so a first post cannot count twice.
- **AND THE COUNTS WERE SERVED FROM A CACHE NOTHING REFRESHED.**
  `InMemoryCatalogueCache` reloads on create/merge/retire/describe, and the
  detail and listing routes read it — so `followerCount` has been stale since it
  was written and `suggested()` has been sorting by it. `setDescription`'s own
  comment names the hazard exactly. Counts come from the row now.
- **Explore is tiles**: one search field, a 2x2 mosaic, the name in the
  interest's colour, the count. **Surface 17**, with a matrix row and a probe —
  `previewForInterests` calls `listByInterest`, so the boundary makes the
  decision it already makes rather than a second one. The matrix is **1,586
  assertions across 17 surfaces**, raised deliberately.
- **The heading says "Busiest interests", not the artboard's "Busy this week"**,
  and the ordering is by post count. There is no seven-day window and nothing
  computes one; shipping the artboard's words over all-time data would be a
  sentence the product cannot back (008/T224).
- **T044 decided**: a new account gets NOTHING, and the empty feed stops
  offering what is not there. "Explore interests" opened a second empty room on
  a fresh install, failing both halves of FR-020 and FR-021 on exactly the
  install they are about. It offers "Share your first photo" when the catalogue
  is empty, and falls back to Explore when it cannot tell.

## Guards that refused this work, correctly

- The touch-target guard would not take an unmeasured `hitSlop` on `Photo`'s
  retry, nor an unsized tile.
- React Native refused `numColumns` changing on one `FlatList` instance — 007's
  second-render lesson; the fix is a distinct `key`.
- **A PREFIX IS NOT A NAME, for the third time here.** `search-result-0` is a
  TILE before typing and a row after, both preserved deliberately, so it is
  ambiguous for the instant between the keystroke and the re-render. It passed
  alone and failed once in a full run — the `share-person-.*` failure in a new
  place. Every caller waits for `interest-list` now, the Maestro flow included.
