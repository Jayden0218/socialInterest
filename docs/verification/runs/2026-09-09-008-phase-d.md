## The design decision Phase D turned around

The plan (T181, T184) had every `toCandidate` construction populate an `authorPrivacy` field
on the candidate. **It was implemented and then removed.**

Privacy is a property of the AUTHOR, not of the post, so carrying it on a candidate means
either denormalising it into every index row — a flip would then need a re-index, which
FR-044 and 001/FR-017 forbid — or asking all thirteen post surfaces to populate a field,
where the cost of forgetting one is that a private account stays public on that surface.
That is the "declared half with no other half" failure this whole feature exists to end, in
the one place where its consequence is a privacy leak.

`RelationshipCache.isPrivateAccount` resolves it inside the boundary instead: memoised per
request beside the follow and block reads, consulted only on a `public` post for a viewer who
is not the author, and **failing closed** if the read throws. The evidence that this was the
right way round is that `privacy-is-not-per-surface.spec.ts`'s allow-list got SHORTER — and
**no read path is on it**.

Neither would have been found by inspection.

- `auth-surface.spec.ts`'s `RequestMethod` lookup had **PATCH and DELETE transposed**. It
  never showed for two features because every route in the public snapshot is a GET — index
  0 — so the only entries the file ever rendered were the ones the mistake could not reach.

  That is 002's first defect in a smaller place: the contract and the API disagreed and each
  looked right alone. Fixed to 403. Two integration tests pinned the old value deliberately
  and now say why they moved; nothing in the app acts on either status for these routes,
  because the product has no moderation UI.
