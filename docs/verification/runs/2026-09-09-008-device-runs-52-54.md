## Every failure so far has been a FLOW bug. Not one has been the product.

That is worth stating plainly, because it is unusual for this project and it is
the thing a reader should check hardest.

| Run | Flow | Cause | Measured how |
|---|---|---|---|
| 52 | `23-multi-photo-post` | US10's description box wrapped the media strip to two rows; `interest-option-0` fell 93pt below a 616 fold | browser at 320×616 |
| 52 | `31-mention` | asserted a NESTED `<Text>` span, which Android renders as a span in one TextView and has no node for | browser proved the link renders |
| 53 | `09-report-and-block` | scrolled down to the block control, then tapped a reason the scroll had taken off the top — 164 vs 852 on a 616 screen | browser at 320×616 |
| 53 | `34`, `35` | `account-privacy` at y=667, `open-moderation-notices` at y=967; `assertVisible` does not scroll | browser at 320×616 |
| 54 | `34-private-account` | **`Screen scroll` wraps the header too**, so scrolling to y=667 took `save-profile` from y=80 off the top | read `primitives.tsx` |
| 54 | `12-interest-from-feed` | scrolled a feed that had not loaded | `09` reaches the same post with a re-polling wait and passed in the same run |
| 54 | `33-mute-and-dismiss` | `post-detail-screen` renders only after `GET /v1/posts/:postId` returns; a bare assert races it | `screens/index.tsx:419` returns `post-loading` until then |

**Run 54's `34` is the half of run 53's fix I got wrong.** I scrolled to reach a
control and did not ask what the scroll had moved away from. The header is inside
the same ScrollView; there is one scroller, not a fixed header over a scrolling
body.

**`23-multi-photo-post` passed in run 54 with no change to it**, having failed in
53 on `media-page-1` after a swipe. Its cause was never established — page 1 was
measured to exist at x=304, one page right — so it is recorded as **a flake that
resolved itself**, not as fixed. If it fails again the swipe is the thing to
look at.
